## Required canonical path

The smallest safe implementation is to keep Practice Replay inside the existing canonical Learning session, AnswerAttempt, EventEnvelopeV2, checkpoint, and History paths. It does not need a table, migration, new event envelope field, new feature ID, or a second progress authority.

1. Create a fresh `learningSessions` row through `ExactPinnedLearningActivityRepository.startExactPinnedSessionWithCheckpoint` (`lib/features/learning/domain/learning_repository.dart:68`, implemented by `DriftLearningRepository`). Revalidate the source terminal Pair checkpoint and every exact lexical identity/revision/checksum before the transaction. Use `activityType = LessonMode.matching.id`; do not encode replay in the route, ID prefix, or activity type.
2. Put the durable Pair session metadata in the versioned Pair checkpoint state already stored as immutable `LearningActivityCheckpoint` events: `purpose = learning|practiceReplay`, nullable `sourceSessionId`, exact content pins, direction, new shuffle seed, round data, and the committed Pair ledger. For replay, require `purpose=practiceReplay`, a different new session ID, a terminal matching source owned by the same owner, and an immutable direct source link. This reuses the 64 KiB/versioned checkpoint boundary in `learning_models.dart:413` and `drift_learning_repository.dart:413–1160`; it changes no database schema or frozen envelope.
3. Persist each cross-side replay answer through the normal `LearningUseCases.recordEvidence` -> `LearningRepository.recordAnswer` path with a new evidence/operation ID, `promptMode=matchingPair`, Pair provenance, and `EvidenceContext.forNewEvidence(evidenceClass: EvidenceClass.recreational, ...)`. Keep recognition/guided details, first-attempt flags, repair state, and star inputs in the typed immutable Pair checkpoint ledger. The AnswerAttempt still retains raw correctness, response time, attempt number, word, owner, and session for History.
4. Let the repository append the canonical AnswerAttempt/EventEnvelopeV2 and rebuild only the replay session outcome. `EvidenceClass.recreational` is the existing central no-op policy: it allows only `sessionOutcome` and `history`, and denies `masterySrs`, `assessmentOutcome`, `activeLearningEffort`, `pronunciation`, `quest`, `streak`, `achievement`, `xp`, and `coins` (`evidence_eligibility_policy.dart:332–343`). This is stronger and safer than adding Pair-specific `if` statements to each reward consumer.
5. Finish through the existing Learning session close. The terminal Pair checkpoint/receipt remains the authority for completion and star projection; generic `learningSessions.correctCount/wrongCount/score` may describe that replay session but must never feed normal latest/best, global accuracy, mastery, reward, Today resolution, or research-primary results.
6. Extend History with a typed Pair projection which decodes the terminal Pair checkpoint and exposes purpose, source lineage, Pair counts, derived stars/version, timer/elapsed, and Review-next status. Group replay rows under the direct source. Compute latest/best from `purpose=learning` only. Do not add columns to generic `LearningHistoryEntry` unless the Pair view is an optional typed field; the smaller boundary is a Pair-specific history model/reader layered on the existing reader.

## Existing safeguards that should remain canonical

- SRS/Mastery: `recordAnswer` calls `rebuildWord` and appends SRS outbox only when the decision set permits `masterySrs`; recreational denies it (`drift_learning_repository.dart:1369–1390`). Recognition and guided evidence already deny mastery too.
- XP/reward/quest/streak: `LearningSideEffectReconciler` resolves the stored decision set before invoking sinks and records `notApplicable` for denied projections. Recreational denies every such projection. Do not bypass the reconciler or call sinks from Pair UI/coordinator.
- Achievement: repository calls `rebuildAchievements` only when permitted on answer insert (`drift_learning_repository.dart:1381`); recreational is denied. Session finish currently performs an unconditional achievement rebuild, but the rebuild filters every attempt through the same decision set, so the replay cannot add an unlock.
- Global accuracy and Weakness: `DriftProgressQueries._loadValidatedPracticeAttempts` rejects `assessment` and `recreational` evidence (`drift_progress_queries.dart:297–338,450–462`), and `DriftReviewCenterReader` likewise excludes recreational wrong attempts. Existing tests already cover this safety floor in `test/features/progress/progress_projector_test.dart` and `test/features/today_hub/today_hub_reader_test.dart`.
- Research primary: construct the event with the existing no-research event context for replay. Recreational decisions never contribute to efficacy outcomes, and Pair replay must not call assessment/motivation measurement repositories, create research rows, or create research outbox operations. No EvidenceContext/EventEnvelopeV2 change is needed.

## Gaps requiring the PM5 extension

1. `DriftLearningHistoryReader.replayAsNewSession` (`lib/features/history/data/drift_learning_history_reader.dart:111`) is an ordinary “repeat lesson” command. It copies the same configuration and derives a new ID, but persists neither `purpose=practiceReplay` nor `sourceSessionId`, does not start atomically, and does not select recreational evidence. Reusing it unchanged would violate durable-purpose, immutable-lineage, and zero-delta requirements. Keep it for its current contract or add a distinct typed Pair replay use case; do not silently redefine all History replay as Practice Replay.
2. `DriftTodayHubReader._loadSession` (`lib/features/today_hub/data/drift_today_hub_reader.dart:154`) selects the latest active Learning session without purpose filtering. A live Practice Replay can therefore become Today’s resumable session. The Pair replay policy must either make this a consciously allowed resume-only presentation with no due-resolution mutation, or the Today reader must exclude Pair checkpoints whose purpose is `practiceReplay`. Because PM5 explicitly requires Today delta zero, the safer testable interpretation is exclusion from Today mission/resolution while Pair owns its own restore entry.
3. Session purpose cannot be inferred from `EvidenceClass.recreational`: a session can exist before its first answer, and other recreational modes already exist. It also cannot be inferred from a session-ID prefix or route. The initial checkpoint must carry purpose and source link from the same atomic start.
4. Generic session outcome is intentionally allowed for recreational evidence. Therefore a “zero delta” assertion must compare canonical global consumers, not demand that the replay’s own session counters/history remain empty. Replay AnswerAttempts, events, checkpoint events, sync outbox for those canonical records, and the replay’s descriptive result are expected writes.

The only real design tension is wording, not a schema contradiction: SDS 15.5 says a Practice Replay answer is “raw/history evidence under purpose,” while the existing central eligibility dimension is evidence class and has no session-purpose input. Classifying the persisted answer as `recreational` preserves raw/history and gives the exact no-op matrix without changing frozen contracts. Keeping it as `recognition` would allow protocol-controlled XP/quest/streak/achievement/coins when `engagementAllowed=true`, so purpose-only metadata would not enforce isolation. PM5 should explicitly adopt recreational as the canonical projection class for Practice Replay while retaining the pedagogical recognition/guided detail in the Pair ledger.

## Follow-up: matching capture and repository replay validation

The existing adapter cannot currently produce valid Practice Replay matching evidence. `CurrentActivityEvidenceAdapter._validateDeclaration` permits `matchingPair` only as `recognition` or `guidedPractice` (`current_activity_evidence.dart:578–584`). Both `captureMatching` (`:1079`) and `restoreMatching` (`:1176`) repeat that allowlist and derive/freeze matching evidence through the research/rollout resolver. Calling `LearningUseCases.recordEvidence` with a handcrafted recreational context would bypass the typed matching capture, its pinned provenance, hint classification, frozen recovery payload, and pending-evidence checkpoint protocol. PM5 must not do that.

The minimal extension is a distinct typed seam on `CurrentActivityEvidenceAdapter`, preferably `capturePracticeReplayMatching` plus `restorePracticeReplayMatching`, rather than widening ordinary `captureMatching` to accept any recreational classification. The new methods should:

- accept the same exact fields as matching capture/restore, including caller-owned evidence ID on restore, canonical content revision, selected/correct identity as represented by the Pair coordinator, response time, attempt ordinal, frozen contexts, and checkpoint-owned owner/actor;
- force `CurrentActivityInput.matchingPair`, `skillId=matching-recognition`, `promptMode=matchingPair`, `providerProvenance=pinned-lexical-matching`, `EvidenceClass.recreational`, and `hintLevel=0`; callers must not choose or override these projection fields;
- require the Pair coordinator to prove from the current checkpoint that `purpose=practiceReplay` and that the pending command belongs to its immutable source-linked replay session before capture/freeze;
- use `LearningEventContext.noResearch` semantics (or an equivalent existing resolver result with no research pins) and reject protocol class overrides/engagement widening for this seam;
- freeze and restore through `FrozenPendingCurrentActivityEvidence` so technical retry preserves the exact operation/evidence/event identity, while a user-requested Practice Replay creates a new session and new identities.

Repository handling also needs one narrow change. `_isValidPinnedDeletedMatchingAnswer` (`drift_learning_repository.dart:1402`) currently accepts only recognition/guidedPractice and checkpoint schemas 1–5. When the Pair checkpoint codec reserves its next version, extend this validator to accept recreational **only when** the same authenticated checkpoint says `purpose=practiceReplay`; retain every existing check for matching activity/prompt/skill/provenance, exact pinned word revision/checksum, pending-evidence key set, selected/correct relation, frozen EvidenceContext/EventContext equality, and owner/actor lineage. Do not simply add recreational to the current class OR condition. That would let an ordinary matching session submit recreational evidence and would weaken the deleted-content pinned path.

For idempotent replay, the repository already has the correct equality boundary: `replayCommittedAnswer` and duplicate `recordAnswer` call `_sameAttempt` (`drift_learning_repository.dart:1164,1252,1858`), which requires exact owner/session/word/prompt/correctness/time/attempt/provenance and canonical EvidenceContext metadata; it then requires the stored canonical event and optional event context to match. PM5 tests should verify the new typed restore returns `inserted=false` for the exact frozen replay command, and rejects changes to purpose, source session, evidence class, content identity, selected target, owner/actor, event context, or operation ID. Purpose/source lineage live in the checkpoint rather than `_sameAttempt`, so the coordinator/repository pinned-checkpoint validation must occur before accepting a first replay write; duplicate replay continues to use exact attempt/event identity.

This follow-up refines the earlier file list: `lib/features/learning/application/current_activity_evidence.dart` and its focused test `test/features/learning/current_activity_evidence_test.dart` are required PM5 seams, and `lib/features/learning/data/drift_learning_repository.dart` plus `test/features/learning/drift_learning_repository_test.dart` require the purpose-gated recreational matching case. The Pair application use case should consume these typed APIs; it should not call generic `recordEvidence` with a constructed context.
