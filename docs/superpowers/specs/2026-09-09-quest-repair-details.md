## Assignment and event semantics

Use timezone calendar constructors for midnight/Monday boundaries, not fixed24-hour additions. Deadline is the earlier of calendar end and assignment plus explicit duration; a recurring quest without duration ends at the calendar boundary. A nonrecurring quest with no duration has no deadline.

Assignment atomically expires prior active periods, checks existing occupancy in any state for this period, and inserts the new instance/progress. Repository insertion must distinguish inserted versus existing rather than silently ignoring an insert and then writing orphan children. Retain opaque instance IDs and existing `quest_complete_<instanceId>_<questId>` reward keys.

Expire and seed only the currently enabled daily catalog at bootstrap and an appropriate foreground/session entry boundary; do not accidentally enable weekly quests or require a restart across midnight.

Use the existing MyApp resumed observer and a bounded optional before-session-start hook on canonical LearningUseCases rather than adding a separate scheduling timer. Pass the pinned expected owner to daily refresh and revalidate after the await before admitting a session. A scheduling failure may leave ordinary learning usable, but owner/lease drift must not be swallowed and followed by admission under the wrong owner. Preserve attached-review identity and reading's atomic start/checkpoint path. No quest success or reward is inferred from a failed refresh.

Evidence windows are half-open: assignment <= occurredAt < deadline. At now >= deadline mark expired. Delayed valid evidence can project against a canonical expired window if its occurrence lies inside it; abandoned rows do not accept new progress. Validate pinned definitions as before. Completed receipts/grants are recoverable by their original source identity; do not revoke historical awards from the old bug.

Once repeated histories exist, filter exact source-event JSON membership in SQL before any result limit. Do not use substring matching or truncate history before matching. UI history can remain bounded50; projection candidates should be bounded by catalog and event-window identity, detecting overlap instead of hiding corruption with LIMIT64.

## Owner merge and lifecycle

Existing owner merge joins by quest ID only and must change. Distinct periods preserve both IDs/progress. Same-period conflicts select a deterministic canonical instance (completed first, stable tie-break), preserve the losing instance/progress as noncanonical, abandon active losers and retain terminal states. Resolve active conflicts before bulk owner rewriting. Never combine progress across windows, rewrite historical reward keys or mint rewards during merge. Record conflict resolution.

Owner compatibility refinement: use persisted keys and valid snapshots to identify logical once-only history; do not infer an unknown legacy type from the current catalog. When an unbound unknown legacy row meets an already-established current occupancy, retain its original key/snapshot/children as noncanonical compatibility history rather than binding it onto an occupied unique key. This is a current occupancy conflict decision, not reconstruction of a historical date or reward. If only unbound legacy rows exist, choose a deterministic canonical compatibility representative and retain the rest noncanonical; the ordinary first-period compatibility rule still applies.

Resolve actual overlapping evidence windows for the same quest explicitly during merge. Rank completed, active, expired, abandoned, then stable instanceId; retain ranked nonconflicting candidates and demote only a candidate that conflicts by logical period, one-shot identity, canonical-active uniqueness, or actual half-open window overlap with a retained candidate. A candidate rejected for overlap must record the conflicting retained ID and reason. Do not merge connected chains indiscriminately: disjoint historical windows remain independent. Unknown metadata never gains new progress/grants; existing receipts remain authoritative. Apply all demotions before owner rewriting, preserving terminal states and every original snapshot/source/reward identity. Test both source/target directions and compatibility replay after merge.

Keep established current-period occupancy distinct from evidence eligibility: a local-calendar completed/expired row occupies its persisted calendar period until periodEnd even when an explicit duration made deadline earlier. Use periodStart/periodEnd for that compatibility decision, deadline only for finite legacy occupancy and evidence-window overlap, and permanent occupancy for once-only history. An active state alone cannot prove the calendar/legacy interval is still current. Test both owner directions with midnight assignment,01:00 deadline,next-midnight periodEnd and noon merge, then repeat assignment without a UNIQUE collision or reward duplication.

Existing aggregate-only quest export stays aggregate-only. Test historical/noncanonical counts, transitive deletion and other-owner isolation. Update current-schema expectations, leaving explicitly historical migration expectations historical.

## Definition history refinement before schema25

Read-only source review found a newly reachable version-history gap: the provider permits catalog version updates and the repository explicitly tests v2 replacing v1 under the same questId. startQuest currently prevents changing an active pin but allows overwrite when only terminal history remains. Recurring periods make that path usable. Existing durable receipts already contain exact grants and remain authoritative; the crash gap after markCompleted and before writing a receipt currently tries to reconstruct old completion against the live catalog and can reject or use the wrong reward if only the version check is relaxed.

Within the same schema25/48-table migration, add nullable `definition_snapshot_json` to quest_instances. Use a bounded strict versioned codec (maximum64KiB UTF-8) containing full definition identity/title/description/type, objective criteria/filters/targets, reward, duration and tags. Record origin as capturedAssignment or migrationCatalog; null means legacyUnknown. Reuse/refactor existing serialization rather than maintaining two inconsistent encoders. New assignment captures the validated definition atomically with its instance/progress. Snapshot content is immutable after capture; ordinary state/progress/owner updates must preserve it. Add the appropriate runtime SQL immutability guard without preventing the one-time migration backfill.

Backfill only a valid stored definition whose catalogVersion matches the historical instance and whose objective IDs/targets match its progress. This is metadata recovered from the stored catalog at migration, not proof of byte-for-byte original assignment content. Missing/mismatched/malformed/oversized definition stays null; preserve all IDs, child progress, existing receipts and awards. Unknown metadata remains visibly unavailable and cannot reconstruct a missing grant or criteria from a newer live definition. A previously valid existing receipt can still reconcile its original grant without that metadata.

Historical/expired projection and history presentation use each candidate's snapshot. Carry that pinned definition or exact grant through QuestProjectionEvaluation into projectionPayload; do not look up a reward by questId in the live catalog after evaluation. Preserve existing receipt shape and reward key. Choose event-window/source candidates before validating an unrelated new active period, so a D1 replay can recover its old receipt without touching D2. Keep existing active-definition mutation rejection. Same-version live definition versus snapshot disagreement must still reject; the snapshot must not become a bypass for same-version content mutation.

Completed receipt recovery uses owner, completed state and exact source membership independently of the current catalog allowlist. A valid completed snapshot may reconstruct its original grant even after its quest is removed from the live catalog; otherwise an empty/current-unrelated catalog can incorrectly persist notApplicable and strand an earned grant. Active or expired-but-incomplete windows still reject a missing current definition. Existing same-version mutation rejection remains. Test empty and unrelated catalogs, more-than100-history earliest/latest recovery, exact-source suffix and other-owner negatives, plus actual durable applied receipt/ledger output.
