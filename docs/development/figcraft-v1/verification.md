## ตรวจระหว่างทำการ์ด

1. ระบุใต้การ์ดว่าใครใช้ฟีเจอร์ ข้อมูลเริ่มต้นคืออะไร เข้าจากหน้าใด กดอะไร ได้ผลที่สังเกตอย่างไร และทั้งปุ่มในแอปกับ Android Back จะพากลับที่ใด ระบุรหัสฟีเจอร์ หน้า FigCraft และไฟล์ Flutter ที่มีเจ้าของ เมื่อหน้าเดียวรองรับหลายงานให้ตรวจผลของแต่ละงาน
2. ใช้ข้อมูลทดสอบที่ระบุเจ้าของได้ เช่น หมวดใหม่สองคำ หลีกเลี่ยงข้อมูลผู้เรียนจริง กรณีโหลดข้อมูลหรือบันทึกให้ลองทั้งครั้งแรก ลองใหม่ และเปิดกลับมาตรวจผล หากเป็นงานออฟไลน์ ให้ตัดเครือข่ายตามลำดับที่จะพบจริง เช่น ดาวน์โหลดโมเดลแล้วจึงปิดเครือข่าย
3. เลือกเทสต์ตามพฤติกรรมที่แก้ รัน Flutter/ติดตั้ง dependencies/สร้างโค้ดทีละคำสั่งต่อ worktree เมื่อแก้ชุดร่วม เช่น shell หรือธีม ให้หยุดผู้เขียนก่อนทดสอบข้ามฟีเจอร์ ตัวอย่างด้านล่างใช้ path จากรากโครงการ

```powershell
flutter pub get
flutter test test/screens/production_shell_navigation_test.dart test/screens/main_navigation_screen_test.dart
flutter test test/screens/offline_vocabulary_journey_test.dart test/screens/quiz_screen_test.dart
flutter test test/screens/learning_loop_layout_test.dart test/screens/accessibility_smoke_test.dart
flutter test test/screens/object_scanner_screen_test.dart test/features/media_practice
```

4. ให้ผู้ตรวจคนอื่นเดินเส้นทางแล้วบันทึกผลก่อนปิดการ์ด หากปุ่มข้ามงานไปหน้าอื่น ให้ย้อนกลับแล้วตรวจตัวกรอง หมวด คำที่เลือก และตำแหน่งเดิมที่ผู้เรียนต้องใช้ต่อ หากเป็นหน้าสรุป ให้ปิดแล้วเปิดอีกครั้งเพื่อตรวจว่าคะแนนและรางวัลถูกบันทึกครั้งเดียว

## ตรวจรอบรวมและเครื่องจริง

บน SHA ที่จะส่งตรวจ ให้หยุดการแก้ไฟล์ รันชุดรวมจากรากโปรเจกต์ดังนี้ CI ใช้ Flutter 3.44.7

```powershell
pwsh -NoProfile -File tool/cli/prepare-field-model.ps1
flutter analyze
flutter test --reporter compact
```

[CI ที่มีอยู่](../../../.github/workflows/ci.yml) ตรวจ PR และตรวจ `push` ไป `main` หรือ `codex/current-code-20261113` สำหรับ branch `codex/figcraft-flutter-prototype` ให้ใช้ draft PR โดยตั้ง base เป็น `codex/current-code-20261113` หลังมี PR การ push งานเพิ่มจะสร้างเหตุการณ์อัปเดต PR ให้ตรวจรอบใหม่ ตรวจผลบนหน้า PR หรือผ่าน `gh pr checks <หมายเลข-PR> --watch` เทียบ SHA ของ PR กับ branch ถ้าใช้ SHA สังเคราะห์ของ GitHub ให้บันทึกทั้งหัว PR และ SHA ที่ CI ทดสอบ ขั้นรวมครอบคลุม Flutter, backend ฝั่ง CPU, Firestore emulator, Supabase ในเครื่องและ Android debug APK

ทดสอบบน Android จริงจาก SHA ที่ผ่านการรวม เริ่มด้วย `adb devices -l` เลือก serial ของเครื่องจริง ตรวจรุ่น ลายเซ็น และข้อมูลแอปเดิมก่อนติดตั้ง หากต้องเก็บข้อมูลของผู้ใช้ให้ใช้แพ็กเกจทดสอบแยกและบันทึกส่วนที่ต่างจาก build ปกติ ห้ามถอนแอปหรือล้างข้อมูลเพื่อข้ามปัญหา downgrade ใช้หมวดสังเคราะห์ที่ระบุรอบทดสอบได้

- **เปิดและบันทึก** เปิดแบบผู้เยี่ยมชม เข้าคลังผ่านเมนูปกติ เพิ่มคำ ปิดแอปแล้วเปิดซ้ำ ตรวจว่าคำยังอยู่ในหมวดเดิม
- **ถ่ายและตัดสินผล** ทดสอบอนุญาต/ปฏิเสธกล้องและเส้นทางกลับ ทดสอบการดาวน์โหลดโมเดลครั้งแรกและใช้ออฟไลน์หลังดาวน์โหลด ให้ผู้ควบคุมวางวัตถุที่รู้ชื่อ บันทึกวัตถุที่วาง ชื่อที่โมเดลตอบและความมั่นใจ ถ้าแสงน้อยหรือโมเดลไม่แน่ใจ ต้องถ่ายใหม่ได้ เมื่อเสนอคำที่มีคำแปล ให้ผู้เรียนยืนยันก่อนเก็บ แล้วกลับไปค้นคำในคลัง
- **ฝึกจนจบ** เริ่มด้วยหมวดที่บันทึกไว้ ตอบทั้งถูกและผิด ตรวจเฉลย ความคืบหน้า จำนวนข้อและคะแนนที่คำนวณจากคำตอบจริง กดกลับหน้าเลือกกิจกรรมแล้วเปิดประวัติ/ผลตามที่มีในขอบเขตการ์ด
- **ทดสอบกับผู้ใช้** เมื่อมีผู้ลองใช้งาน ให้โจทย์ เช่น “เก็บคำจากสิ่งที่เห็นแล้วนำไปฝึก” สังเกตว่าเริ่มจากเมนูไหน ต้องให้คำใบ้ตรงไหน และกลับถึงคลังด้วยตัวเองไหม บันทึกผลการสังเกตเป็นรายงาน UAT เมื่อมีผู้ใช้ทำจริง การใช้ผลเพื่อวิจัยผู้เรียนและการเปิดรับผู้เข้าร่วมต้องเป็นไปตามการอนุมัติของโครงการ

## สรุปผล แก้ปัญหา และย้อนการเปลี่ยนแปลง

บันทึกในการ์ด **รหัสฟีเจอร์/งาน → จุดเริ่ม → สิ่งที่กด → ผลที่เห็นและข้อมูลที่บันทึก → ทางกลับ → SHA/อุปกรณ์/สภาพเครือข่าย → หลักฐาน → ผลการตรวจ** ระบุ `ผ่าน`, `ต้องแก้` หรือ `ยังไม่ตรวจ` ให้คำนวณความครบถ้วนจาก **รายการในขอบเขตที่ผ่าน / รายการทั้งหมดในขอบเขตเดียวกัน** จำนวนเฟรม จำนวนคลิก และรายงานรุ่นเดิมใช้เป็นดัชนีค้นหลักฐาน ถ้ายังมีงานที่เลื่อนหรือยังขาดเครื่อง ให้คงไว้ในตัวหารของขอบเขตนั้นและบอกว่าขาดอะไร

| ผลกระทบ | การดำเนินการ |
| --- | --- |
| ข้อมูลผู้อื่นรั่ว สูญหาย ซื้อ/รับรางวัลซ้ำ หรือมีข้อมูลวิจัยโดยขาดสิทธิ์ | หยุดการเขียนในเส้นทางนั้นทันที เก็บหลักฐานที่ไม่มีข้อมูลส่วนบุคคล ตรวจสถานะจริงก่อน retry และส่งคืนการ์ดให้ผู้รับผิดชอบ แก้และตรวจขอบเขตข้อมูลก่อนรวม |
| แอปล้ม เข้าไม่ถึง ทำงานไม่จบ ย้อนผิดหน้า หรือผู้ใช้ TalkBack/ตัวอักษรใหญ่ทำงานต่อไม่ได้ | ให้สถานะ `must-fix` ทำซ้ำจากทางเข้าปกติ แก้สาเหตุ ตรวจกรณีเดิมและงานข้างเคียงบน SHA ใหม่ |
| ความต่างทางภาพที่ผ่านเกณฑ์และไม่ขัดการอ่านหรือการใช้งาน | ผู้ตรวจบันทึกข้อแตกต่างและเหตุผล กำหนดผู้รับผิดชอบเมื่อจำเป็นต้องติดตาม หากกระทบเกณฑ์ภาพของการ์ดให้คืนแก้ |

เมื่อคำสั่งสะดุด ให้ตรวจสาเหตุและสถานะก่อนลองใหม่ตาม AGENTS.md การเปิดหน้าค้างไม่เกินกำหนดเฝ้าดูเพียงอย่างเดียวยังไม่ใช่หลักฐานว่าคำสั่งหยุดทำงาน หากต้องย้อน UI ที่รวมแล้วให้สร้าง commit ย้อนเฉพาะชุดการเปลี่ยนแปลง จากนั้นทดสอบฐานข้อมูลเดิมและเส้นทางเดิมในเครื่องทดสอบก่อนรวม ถ้า schema เดินหน้าไปแล้วให้แก้ด้วย migration ที่รักษาข้อมูลและรองรับรุ่นที่ใช้อยู่

ปิดต้นแบบเมื่อทุกงานที่ตกลงรับในรุ่นนี้มีผลและทางกลับบน Flutter ปิด `must-fix` แล้ว และมีการตรวจบน SHA ที่ส่งมอบจริง การอนุมัติปล่อยแอป ข้อมูลผู้เข้าร่วม และประสิทธิผลทางการเรียนมีหลักฐานและผู้อนุมัติแยกกัน
