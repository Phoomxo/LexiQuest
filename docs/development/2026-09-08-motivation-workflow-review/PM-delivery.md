## ลำดับส่งมอบแบบมีเงื่อนไข

**ระยะ 0 — ยืนยันปัญหาและขอบเขตที่ตรวจได้:** ทดสอบความเข้าใจต้นแบบกับเด็กไทยที่เหมาะกับเนื้อหาจริง รวมผู้เริ่มต้น ผู้มีเส้นตาย และผู้ใช้เวลาหรือเครื่องร่วมไม่แน่นอน
แยกกลุ่มตามบริบทที่เกี่ยวกับงาน ไม่เหมารวมเด็กไทยจาก persona ผู้ใหญ่ U3; เก็บ baseline การเริ่มเรียน ความเข้าใจผล และอุปสรรคก่อนกำหนดเกณฑ์ตัวเลข
ผลส่งมอบคือเส้นทางหลักหนึ่งชุดและ prototype ที่ผ่าน design review ก่อน implementation พร้อมข้อเท็จจริง/สมมติฐาน/acceptance แยกกัน; ไม่รอการศึกษาประสิทธิผลเพื่อแก้ UI ที่มีหลักฐานชัด

**ระยะ A — เข้าเรียนง่ายและเห็นผลตรงจริง:** P4 ลดรายการทบทวนที่ขวางทางเริ่มด้วย summary/preview และดูทั้งหมด ใช้ recovery เดิมโดยไม่เปลี่ยน due date หรือ mark done
P1 เติม goal/Today เฉพาะข้อมูลที่มีและวันเวลาที่เข้าใจง่าย เป้าหมายข้ามได้; P2 แสดงข้อเท็จจริงสำคัญหนึ่งเรื่องพร้อมเหตุผลเลือกงานจากระบบเดิม
รักษา resume/assigned ที่มีสิทธิ์และ active session; ไม่เพิ่ม onboarding แผนหรือการ์ดหลายชุดก่อนปุ่มเริ่ม และไม่สัญญา “จบในกี่นาที” หากมีเพียงจำนวนข้อ
คุณค่าที่ต้องเห็น: ผู้เรียนเริ่มหรือเรียนต่อได้โดยไม่ต้องจัดตารางก่อน และอธิบายได้ว่าผลใดเป็นการเรียน ผลใดเป็นรางวัล; ไม่ต้องทำคิวทั้งหมดเพื่อจบรอบ
ความเสี่ยง: summary ซ่อนงานสำคัญ, ข้อความ recovery ขัดตัวเลข, เวลาแสดงไม่ตรงเวลาเตือน; ต้องตรวจจริงก่อนขยายการเปิดใช้ [U1–U3]

**ระยะ A เสริม — P5 ภาพจริงในพื้นที่เดียว:** อวาตาร์กับของที่ถือครอง/เลือกใช้จาก reward authority เดิม พร้อม preview ไม่ซื้อและ fallback ชื่อเมื่อภาพไม่พร้อม
ทำควบคู่เฉพาะเมื่อ renderer/assets แยกจากงานทางเริ่มเรียนและมีผู้รับผิดชอบตรวจได้; หากแย่งความพร้อมของระยะ A ให้เลื่อนเฉพาะ P5 ไม่เลื่อนทั้งวงจร
ชิ้นนี้จบได้โดยไม่ทำภาพทุกชนิดหรือธีมทั้งแอป แต่ต้องระบุรายการที่รองรับตรงจริง และไม่สื่อว่าของที่ยังไม่รองรับเปลี่ยนรูปลักษณ์แล้ว
คุณค่า: ซื้อ/สวมใส่แล้วรับรู้ผลและแสดงตัวตนได้; ตรวจ offline/จอเล็ก/ภาพสำรอง/owner switch และไม่กดปุ่มเริ่มเรียนให้หายไป [U5,C3]

**ระยะ B — เลือกลงทุนจากปัญหาที่เหลือ:** หากเด็กต้องการคำแนะนำว่าเรียนอะไร ให้ P3 เริ่มจากทางเลือกกิจกรรมเดิมที่สัมพันธ์กับ review/เป้าหมาย โดยเหตุผลชัดและปิดได้
หากเด็กตั้งเป้าหมายแล้วจัดงานข้ามวันไม่ได้ จึงพิจารณา P1 ตารางสัปดาห์ที่แก้/ข้ามได้ พร้อมนิยามความสัมพันธ์ goal–session–review ก่อนสร้างสถานะถาวร
สองทางนี้ไม่จำเป็นต้องส่งพร้อมกัน; ผู้เตรียมสอบอาจต้องการแผนก่อน ส่วนผู้สำรวจอาจต้องการทางเลือกก่อน ใช้ข้อมูลผู้ใช้ตัดสิน ไม่ใช้คะแนนโหวต persona
การเพิ่ม objective/reward ผ่าน Quest authority และ catalog version เท่านั้น; หนึ่งกิจกรรมตอบหลายเหตุผลได้ แต่เครดิตยังเป็นไปตาม eligibility เดิม ไม่สร้างงานหรือรางวัลซ้ำ
ความเสี่ยง: แผนกลายเป็นหนี้ ภารกิจชวนเลือกข้อง่ายแทน review หรือเปลี่ยน recognition เป็น recall ในข้อความ; ย้อนกลับได้ด้วยการเอาชั้นแนะนำออกโดยเก็บหลักฐานเดิม

**ระยะ C — P6 ตัดสินแยก:** เริ่มจากสถานการณ์จำลอง/ต้นแบบไร้บัญชีเด็กและข้อมูลสังเคราะห์เพื่อดูว่า “เรียนกับเพื่อน” ช่วยปัญหาใดจริง
ทำ spec ใหม่เฉพาะเมื่อมีคุณค่าที่เด็กยืนยันและโครงการดูแลได้; เงื่อนไขขั้นต่ำคือ opt-in, solo เท่าเทียม, ปฏิเสธ/ออกได้ และไม่เผยจุดอ่อนหรือการหายไป
ยังไม่เลือกว่าใช้ friend graph/ห้อง/chat; ไม่ตั้ง shared streak หรือโบนัสทีมที่ลงโทษคนพัก ไม่ดึงรายชื่อ และไม่เชื่อมการชวนเพื่อนกับรางวัล
ผลตัดสินอาจเป็นทำต้นแบบต่อ เลื่อน หรือไม่ทำ โดยไม่มีหนี้ว่าต้องส่งให้ครบ P1–P6; การดูแลเด็กและข้อมูลเป็นงานผลิตภัณฑ์จริง ไม่ใช่รายการท้ายโครงการ [H2,U5]

## เกณฑ์ความสำเร็จและวงจรรับฟัง

- **การใช้งาน:** เด็กเริ่ม/เรียนต่อ หยุด และกลับ Standard ได้จากสถานการณ์จริง; บันทึกจุดหลงทาง การขอความช่วยเหลือ และความเข้าใจเวลา/ผล เปรียบเทียบ baseline เดิม
- **การเรียน:** ใช้หลักฐานที่มีขอบเขตเนื้อหา ชนิดกิจกรรม ตัวช่วยและช่วงเวลาชัด; หากจะอ้างจำดีขึ้นต้องตรวจการจำภายหลังอย่างเหมาะสม ไม่ใช้ XP/streak/การซื้อเป็นตัวแทน
- **แรงจูงใจ:** รับฟังความเต็มใจ ความรู้สึกเลือกได้ ความสนุก และแรงกดดันด้วยวิธีเหมาะกับวัย; การจบ quest หรือกดหน้าแต่งตัวมากขึ้นยังไม่ยืนยันข้อเหล่านี้
- **การกลับมาใช้:** ดูการกลับมาเริ่มกิจกรรมที่มีความหมายตามช่วงติดตามที่ตกลง และบริบทการเข้าถึงอุปกรณ์; แยกจากการเปิด notification และไม่ตีความวันหายเป็นความล้มเหลวของเด็ก
- **วงจรตัดสิน:** สังเกตงานจริง → สรุปปัญหาตามกลุ่มโดยไม่ใส่ PII → ให้ผู้ใช้ตรวจความเข้าใจ → ปรับต้นแบบ → ตรวจซ้ำ → คง/เปลี่ยน/เลื่อนแต่ละ P พร้อมเหตุผล
- กำหนดเกณฑ์ผ่านและหยุดก่อนทดลอง หลังมี baseline; ตัวเลขตัวอย่างหรือความเห็น persona ไม่ใช่ประมาณการผลลัพธ์ และไม่เก็บ research telemetry ใหม่เพียงเพื่อวัดแผนนี้

## Cross-review และข้อสรุปหลังโต้แย้ง

อ่าน `03-cross-review-brief.md`, `02-design-evidence.md`, BA/U5/SA/QA แล้ว; ข้อสรุปนี้ยกระดับ design gate ของแผนเดิมและแทนข้อความที่ขัดกัน
**SA โต้ขอบเขต P1/P4:** PM เดิมยังอาจเรียกการ์ด goal ว่าแผน และรวมฟอร์มเตือนกับตารางวนซ้ำ; ยอมแก้ตารางขอบเขตให้ goal card/เตือนครั้งเดียวแยกจาก adaptive weekly plan/recurrence อย่างชัดเจน
**BA โต้การเดาปัญหา:** รับให้เสียงเด็กไทยและบริบทการเรียนเป็นเกณฑ์เลือก P ถัดไป ไม่ใช้ population data หรือ persona ตัดสินแทน; discovery ไม่ขวางการแก้ UTC/ลำดับปุ่มที่ตรวจพบแล้ว และยังไม่อ้างช่วงอายุที่อนุมัติ
**U5 โต้การเลื่อนความสนุก:** คง P5 ภาพนิ่งของที่ใส่จริงหนึ่งพื้นที่ในระยะแรกแบบมีเงื่อนไข; ยอมให้ความเรียบร้อยของภาพเป็น deliverable แต่ไม่ยอมให้ asset ทั้งร้านขวางทางเริ่มหรือเพิ่มรางวัลเพื่อพิสูจน์คุณค่า
**QA โต้ความพร้อม:** ยอมเพิ่มต้นแบบและภาพทุกสถานะก่อน implementation พร้อมตรวจภาพจริงหลังทำ; screenshot/golden/token ผ่านแสดงได้เพียงคุณภาพตามขอบเขตที่ตรวจ ไม่ใช่ UX ของเด็กหรือผลการเรียนผ่าน
**Phase แรกที่รับ:** Learn/Today หนึ่ง canonical next action → goal/เตือนครั้งเดียวที่ข้ามได้ → lesson/result → กลับมา; P5 เสริมเมื่อแยกงานได้ ไม่มี adaptive plan, quest objective ใหม่ หรือ online P6
เลือกแนว “เป็นมิตร มีโครงสร้างชัด” ตาม design evidence: ห้าแท็บเดิม ภาษาไทย hierarchy/spacing/type/icon สม่ำเสมอ และจังหวะเลือก–ตรวจ–ผลที่คุ้นเคยจาก Duolingo/ALLTCAS ไม่สร้าง path/หลักสูตรปลดล็อกปลอม
Nielsen ใช้ตรวจความคุ้นเคย/การควบคุม; SDT ใช้ถามเรื่องเลือกได้ เห็นความสามารถจริง และได้รับการสนับสนุน ทั้งสองเป็นเหตุผลออกแบบตามแหล่งใน `02-design-evidence.md` ไม่ใช่หลักฐานว่า LexiQuest เพิ่มแรงจูงใจแล้ว
**D0 ก่อนพัฒนาแต่ละชิ้น:** ทำภาพ/prototype ของหน้าที่เลือก พร้อมเนื้อหาจริงและ empty/pending/error/retry/disabled แล้ว review เส้นทาง/ข้อความตรง contract ภายใน; เป็นงาน design ที่ทำได้ในเครื่อง ไม่ใช่การขออนุมัติใหม่ทั้งโครงการหรือรอ human acceptance
**D0 acceptance:** เปรียบเทียบ390×844/text100 และ360×800/text200/คีย์บอร์ดเปิด; ตรวจ action/back, contrast, type/icon/spacing และ reduce-motion variants โดยไม่ย่อฟอนต์/ซ่อน label เพื่อให้ภาพพอดี
**D1 เสียงผู้ใช้:** เมื่อมีกลุ่มผู้ยินยอมและกระบวนการที่เหมาะสม ตรวจต้นแบบให้เด็กเริ่ม/กลับ/อ่านผล/แยกลองดู–ซื้อได้โดยไม่บอกตำแหน่ง; บันทึกการช่วยเหลือ ความลังเล และความรู้สึกแยกกันก่อนขยาย UX ที่ยังเป็นสมมติฐาน
อายุหลัก/สัมภาษณ์/UAT ที่ยังไม่พร้อมจำกัดข้ออ้างความเหมาะสม ไม่ห้าม bounded local prototype หรือแก้ UI ที่มีหลักฐานเมื่อผู้ใช้อนุมัติพัฒนาต่อ; รับฟังคู่ขนานและแก้เมื่อพบเด็กเข้าใจผิด ไม่รอ efficacy หรือสมมติว่า D1 ผ่าน
**D2 หลังทำ:** ตรวจหน้าจอ/การกดจริงเทียบ prototype พร้อม canonical data oracle สำหรับ retry/replay/owner switch/offline/เวลา; ตรึง UI หลังแก้ข้อพบแล้วจึงทำ final-system gates บน source/flags/APK เดียวตาม QA
**D3 ตรวจรับเปิดใช้:** native/TalkBack/อุปกรณ์จริงและ learner UAT ตาม dependency ต้องมีหลักฐานรุ่นนั้นก่อนอนุมัติระดับ rollout ที่เกี่ยวข้อง; gate ไม่พร้อมให้ pending เฉพาะส่วน และไม่มีการเปิด Research/enrollment/upload อัตโนมัติ
สิ่งที่ไม่ยอมแลก: Standard/5แท็บ/8–44/authority/frozen contracts/ข้อมูลเจ้าของ; ไม่ใช้ XP/ชุด/retention แทน mastery ไม่ให้ supplemental voice/replay สร้างเครดิต และไม่เปลี่ยน exposure วิจัยผ่านงาน polish โดยไร้การทบทวน
ข้อยุติ PM: รับ functional, visual และ usability acceptance เป็นคนละหลักฐานที่ต้องตรวจครบตามระยะ; P6 คง discovery สังเคราะห์แยกและยุติได้ ความยั่งยืนรับใช้การเรียนของเด็ก ไม่ตั้งเป้ารายได้หรือ claim learning efficacy จากรอบเอกสารนี้
