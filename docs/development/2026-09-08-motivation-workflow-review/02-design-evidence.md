# UX/UI evidence and proposed design criteria

วันที่ 8 กันยายน 2026 — เพิ่มตามคำชี้แจงผู้ใช้ระหว่างการวิเคราะห์ เป็นข้อเสนอให้สิบฝ่ายโต้แย้งและ S11 ตัดสิน ยังไม่ได้สร้างหน้าจอใหม่หรือแก้แอป

## เป้าหมาย

ผู้เรียนควรคุ้นเคยกับวิธีใช้ เข้าใจงานหลัก รู้สึกว่าแอปมีการออกแบบอย่างเสร็จเรียบร้อย และมีความสนุกพอเหมาะกับวัย การทำงานถูกต้องเพียงอย่างเดียวไม่ใช่เกณฑ์จบงานดีไซน์ ขณะเดียวกันความสวยไม่ทดแทนการเข้าถึง การเรียนจริง หรือความซื่อตรงของผลที่แสดง

## แหล่งต้นแบบและสิ่งที่นำมาปรับ

- [Duolingo core tabs redesign](https://blog.duolingo.com/core-tabs-redesign/): ทีมออกแบบอธิบายการทำตำแหน่งหัวข้อ ลำดับตัวอักษร และระยะห่างให้สัมพันธ์กัน รวมทั้งใช้พื้นที่ว่างแทนการตีกรอบทุกส่วน และชั่งความเรียบง่ายกับความชัดเจน นำวิธีคิดนี้มาใช้กับ Learn/Today/ผลเรียน/ร้าน ไม่ถือว่าต้องวาดภาพหัวหน้าทุกแท็บหรือเหมือนกันทุกจุด
- [Duolingo home redesign ปี 2022](https://blog.duolingo.com/new-duolingo-home-screen-design/): guided next step ช่วยตอบว่าจะทำอะไรต่อ นำมาปรับเป็น next action จาก recommendation/resume/review เดิม ไม่วาดเส้นทางหลักสูตรหรือปลดล็อกด่านที่ข้อมูลเราไม่ได้รองรับ
- [ALLTCAS เว็บไซต์ทางการ](https://alltcas.com/): เนื้อหาที่ตรวจมีโจทย์ คำอธิบายทีละขั้น คำศัพท์พร้อมตัวอย่าง สถิติอ่านหนังสือและกิจกรรมกับเพื่อน ใช้เป็นกรอบงานที่ผู้เรียนรู้จัก ไม่อ้างว่า root ได้เดิน native app ทุกหน้าหรือว่าสี/spacing ของเว็บเท่ากับแอป
- ความนิยมและผลสำรวจที่ผู้ใช้กล่าวเป็นข้อมูลจากเจ้าของโครงการ รอบนี้ไม่มี raw questionnaire/กลุ่มตัวอย่าง จึงไม่อ้างอันดับตลาดหรือผล UAT ของเด็กไทยทั้งหมด

## หลักการที่ใช้และขอบเขตการตีความ

| หลักการ/แหล่ง | ผลต่อการออกแบบ LexiQuest |
| --- | --- |
| [Nielsen heuristics — consistency, match to user language, recognition, control, minimalist design](https://www.nngroup.com/articles/ten-usability-heuristics/) | คงปลายทาง/ชื่อปุ่มสม่ำเสมอ ใช้วันที่ท้องถิ่นแทน UTC code มีปุ่มย้อน/เปลี่ยนคำตอบ ใช้ภาพ+labelที่คุ้นเคยและจัดความสำคัญ; heuristic เป็นแนวตรวจ ไม่ใช่ผลทดลองกับผู้ใช้เรา |
| [Ryan & Deci 2000 — Self-Determination Theory](https://selfdeterminationtheory.org/SDT/documents/2000_RyanDeci_SDT.pdf) | ใช้ autonomy/competence/relatedness เป็นคำถามออกแบบ: เลือกและพักได้ไหม เห็นสิ่งที่ทำได้จริงไหม ได้รับการสนับสนุนไหม; ไม่อนุมานว่า avatar เท่ากับความสัมพันธ์หรือว่ามีสามฟีเจอร์แล้วเพิ่มแรงจูงใจแน่นอน |
| [W3C SC2.3.3 animation from interactions](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html) | ใช้แนวทางหยุด motion ที่ไม่จำเป็นและเคารพ reduce motion; ข้อนี้เป็น WCAG ระดับ AAA สำหรับเว็บ ไม่ใช่คำรับรองว่าแอปผ่าน WCAG ทุกข้อ |
| [Flutter accessibility](https://docs.flutter.dev/ui/accessibility) และ policy ภายใน M3Theme | ตรวจทั้ง semantics/layout/input และใช้งานกับเทคโนโลยีช่วยเหลือจริง เกณฑ์ขนาดปุ่ม48 logical pixels มาจาก policy ปัจจุบันของโครงการ ไม่อ้างว่า web criterion ทั้งหมดใช้หน่วยเดียวกัน |

ข้อแยกสำคัญ: recognition ใน UX หมายถึงช่วยจำวิธีใช้/ชื่อเมนู ไม่ใช่เหตุผลเอาเฉลยหรือตัวเลือกไปแสดงในแบบฝึกที่ต้องวัด independent recall ภาระการใช้แอปกับความยากที่ตั้งใจให้ฝึกเป็นคนละเรื่อง

## ทางเลือกเพื่อให้ S11 ตัดสิน

1. **เรียบมาก เน้นรายการ:** เปลี่ยนน้อยและโหลดเบา แต่ถ้ามีแต่กล่อง/สถิติ/ข้อความอาจยังให้ความรู้สึกดิบและเหมือนงานเพิ่ม
2. **เป็นมิตร มีโครงสร้างชัด:** คง5แท็บ โทนสีเดิม พื้นที่ว่างและลำดับตัวอักษรสม่ำเสมอ หนึ่งปุ่มหลักต่อจังหวะ มีภาพ/ตัวละครขนาดเล็กเมื่อช่วยสื่อความหมาย และ motion เฉพาะ feedback — root เสนอให้ทบทวนเป็นตัวเลือกหลัก
3. **เกมเต็มหน้าพร้อมเส้นทาง/สังคม:** อาจน่าสนใจสำหรับบางกลุ่ม แต่เปลี่ยน mental model มาก ต้องมี content progression/online/asset lifecycle ที่ตรงจริง และอาจเบียดงานเรียนเดิม จึงไม่ควรเท่ากับ “แค่ปรับ UI”

## ข้อกำหนดหน้าจอที่เสนอ

- **Learn:** หนึ่ง next action เด่น (งานค้าง/ทบทวน/คำแนะนำตาม authority); เลือกฝึกเองยังอยู่ กลุ่มภารกิจ/แผนเป็นข้อมูลประกอบ ไม่เพิ่มหลาย hero cards ข้อความเหตุผลผูกเป้าหมายได้ต่อเมื่อมี mapping จริง
- **Today:** จัดงานทบทวนจำนวนมากเป็นสรุปและทางเปิดรายการเดิม; ปุ่มเริ่มไม่อยู่ท้ายรายการยาว แผน/วันกำหนดเป็นส่วนที่กางได้ การยุบไม่ลบ due items หรือข้าม canonical priority
- **Goals/reminders:** date/time picker ท้องถิ่นพร้อมสรุปวันที่/เวลา อ่านและแก้ได้ แยก deadline ครั้งเดียวจากตารางเรียนวนซ้ำที่ยังต้องมี contract ใหม่
- **Lesson:** progress/โจทย์/คำตอบ/ตรวจ/feedback/ต่อไปอยู่ตำแหน่งคาดเดาได้; แถบ action ต้องไม่ทับเนื้อหา/คีย์บอร์ด ไม่มีการบังคับพูดหรือเปลี่ยนวิธีให้คะแนน
- **Result:** บอกสิ่งที่ทำจริงหนึ่งเรื่องพร้อมบริบทและ next action; บันทึกอยู่/ยังไม่มีข้อมูล/เทียบไม่ได้แสดงตรงจริง; ฉลองไม่หน่วงการกดต่อและไม่แสดงรางวัลก่อน commit
- **Avatar/shop:** preview อ่าน equipped/ownership เดิม แยก “ลองดู” จาก “ซื้อ” ด้วยคำชัด ของ/ภาพไม่พร้อมยังอ่านชื่อและกลับเรียนได้ ไม่โหลดภาพทั้งร้านก่อนเริ่มบทเรียน

Root ตรวจ catalog v2 จริงที่ `lib/features/rewards/domain/reward_models.dart:40`: มี `theme_default`, `theme_ocean`, `wallpaper_focus`, `headgear_ipa`, `weapon_cefr`, `armor_srs` อยู่แล้ว ชื่อ IPA/CEFR/SRS และ Material 3 ต้องประเมินความเข้าใจของผู้ใช้; ถ้าทำคำอธิบายใน presentation ให้อ่านง่ายต้องรักษา ID/version/ราคา/สิทธิ์เดิม ไม่แก้ frozen snapshot เพื่อทำ localization และไม่สัญญาว่า theme ทั้งแอปเปลี่ยนเมื่อทำเพียง avatar preview ขอบเขตเล็กสามารถเริ่มตัวละครพื้นฐานและ preview อุปกรณ์หนึ่งชนิดที่มีอยู่ โดยแสดงสถานะยังไม่เป็นเจ้าของตามจริง

## ค่าตั้งต้นสำหรับต้นแบบ ไม่ใช่ข้ออ้างว่าผ่านการทดสอบแล้ว

- ใช้ M3Theme/NotoSansThai และ semantic colors เดิม; เลือก spacing จาก4/8/12/16/24/32 logical pixels ให้มีระบบ โดยเริ่ม page/card padding16และกลุ่มใหญ่24; ปรับตามจอ/ภาษา ไม่ยึดเลขจนตัดเนื้อหา
- body ตั้งต้น16, title20–24, ใช้น้ำหนัก/ขนาดไม่กี่ระดับ และขยายตาม OS; radius16อ้าง theme เดิม เลือก outline/เงาตามระดับความสำคัญไม่ซ้อนทุกกล่อง
- เป้ากดอย่างน้อย48×48 logical pixelsตามtheme; icon-onlyต้องมีlabelที่อ่านออกและ tooltip ตามบริบท สถานะเลือก/ผิด/ถูกไม่ใช้สีอย่างเดียว
- motion ทดลอง150–200msสำหรับการเลือก/เปลี่ยนสถานะเล็ก ๆ ไม่มี idle loop/เสียง auto; เมื่อ reduce motion เปิดใช้ค่าศูนย์หรือภาพนิ่งที่สื่อสถานะเท่ากันผ่าน helper เดิม; เวลาเป็น design candidate ไม่ใช่ค่าที่พิสูจน์ดีที่สุด
- เก็บทั้ง normal/high contrast, light/dark และ reduced motion แยกกัน การ harmonize สไตล์ไม่ลดความสามารถในการเข้าถึง

## เกณฑ์ design acceptance ที่เสนอ

1. มีภาพและ prototype ของ Learn/Today, goal form, lesson/result, avatar states ก่อนใช้เป็นเป้าการ implement; review content จริง รวม empty/pending/error/retry/disabled ไม่ใช้แต่หน้าที่มีข้อมูลสมบูรณ์
2. เปรียบเทียบ390×844/text100 กับ360×800/text200, คีย์บอร์ดเปิด, TalkBack order และ back/exit; ไม่ overflow/ทับปุ่ม ไม่ย่อฟอนต์หรือซ่อนชื่อแท็บเพื่อให้ภาพพอดี
3. ผู้ทดสอบเป้าหมายที่ยินยอมสามารถเริ่ม/เปลี่ยนคำตอบ/อ่านผล/กลับมาเรียน/ปิดเตือนได้โดยไม่มีการบอกตำแหน่งปุ่ม; รายงานการช่วยเหลือ ความลังเล ความผิดพลาดและความรู้สึกต่อดีไซน์แยกจากผลเรียน
4. ตรวจ overlay/spacing/type/icon/สีจาก artifact เทียบ prototype และ code state จริง; theme tokens ผ่านอย่างเดียวไม่เท่ากับ polish ผ่าน
5. ผู้ใช้ที่ไม่ชอบ avatar/ไม่มีเน็ต/ไม่ใช้เสียงยังได้ workflow และผลหลักเท่ากัน; ปิด motion ไม่เสีย feedback; ปรับดีไซน์เสร็จแล้วจึงรัน final system gates บน source เดียวกัน
