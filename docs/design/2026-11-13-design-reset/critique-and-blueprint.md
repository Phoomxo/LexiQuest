## เหตุที่ต้องเปลี่ยนโครงออกแบบ

LexiQuest มีแนวคิดเก็บคำ ฝึก เห็นผล และฝึกต่อจากหลักฐานที่เชื่อมกัน แต่ UI จัดหน้าเป็นรายการฟังก์ชันและบัตรตัวเลขมากเกินไป ผู้เรียนยังต้องตีความเองว่าควรทำอะไรต่อ การแก้สี ถ้อยคำ และมุมโค้งทีละจุดจึงไม่เพียงพอ

คำวิจารณ์ของกรรมการทั้งสามเป็นข้อมูลที่ผู้ใช้รายงาน รอบนี้ยังไม่มีบันทึกคำวิจารณ์รายข้อหรือภาพที่กรรมการตรวจ จึงไม่อ้างว่าผู้ตรวจ AI ชุดนี้แทนกรรมการ หรือยืนยันสาเหตุทั้งหมดของคำตัดสินนั้นได้

หลัก Attack the Premise เปลี่ยนสมมติฐานจาก “ไม่ล้นและทดสอบผ่านจึงออกแบบเสร็จ” เป็น “ต้องพิสูจน์ว่าแต่ละหน้าช่วยให้ผู้เรียนตัดสินใจและทำงานได้ดี” หลัก Experience First ทำให้จัดหน้าตามงานของผู้เรียน แทนจัดตามโมดูลที่เขียนไว้แล้ว

## ข้อเสนอระบบใหม่ที่รอการเลือกทิศทางภาพ

คงชื่อ LexiQuest และวงจร “เก็บคำ → ฝึก → เห็นหลักฐาน → ฝึกต่อ” เป้าหมายภาพคือให้ผู้เรียนเห็นคำ ชุดฝึก และความคืบหน้าที่เข้าใจได้ทันที ไม่ใช้ภาพเกมหรือ dashboard ทั่วไปเป็นเหตุผลในการจัดหน้า

ข้อจำกัดล่าสุดของผู้ใช้คือเมนูภาษาไทยที่เป็นธรรมชาติ และเลย์เอาต์ที่เชื่อมต่อกันโดยไม่เว้นช่องว่างเสียพื้นที่ ให้ใช้ “วันนี้”, “คลังคำ”, “ความก้าวหน้า” และ “บัญชี” เป็นชุดชื่อทดลอง ใช้ “ผลการฝึกครั้งนี้” เป็นชื่อผลของหนึ่งรอบ และใช้ “ประวัติการฝึก” เฉพาะรายการเรียงตามเวลา แสดงชื่อเทคโนโลยีเฉพาะเมื่อผู้ใช้ต้องตัดสินใจเรื่องข้อมูลหรือการตั้งค่าจริง ข้อความอย่าง “เริ่มฝึกคำนี้” มีหน้าที่ชัดกว่าการแปลชื่อโมดูลตรงตัว

คำแนะนำคือจัดหน้าเป็นกลุ่มเนื้อหาที่เชื่อมกันด้วยแนวจัดวางร่วม ระยะห่างตามความสัมพันธ์ และบริบทคำเดียวกัน ลดกรอบที่แยกทุกส่วนและพื้นที่ว่างระหว่างหัวข้อกับงานจริง ให้งานแนะนำจาก AllTCAS นำการเริ่มต้น ใช้จังหวะโจทย์และ feedback จาก Astra กับ Lingo Trail โดยไม่ยืมภาพลักษณ์รางวัลของงานสร้างกลับ การเชื่อมต่อไม่ได้หมายถึงอัดข้อความจนแน่นหรือทำ touch target เล็กลง

เปรียบเทียบแบบศึกษาภาพที่แก้ไขได้อย่างน้อยสองแบบบนข้อมูลเดียวกัน แล้วให้ผู้ประสานงานเลือกคำแนะนำจากหลักฐานโดยไม่ถามความชอบเพิ่มเติมตามคำสั่งผู้ใช้ ตรวจทั้งหน้าเรียน หน้าฝึก ภาษาไทยยาว และข้อมูลว่าง ไม่เลือกจากหน้า cover เพียงหน้าเดียว แบบศึกษา SVG สำหรับ Figcraft ยังไม่ใช่งานออกแบบครบ 48 หน้าหรือไฟล์ที่ sync แล้ว

## ลำดับดำเนินงานและตรวจรับ

1. **ยืนยัน baseline และเส้นทางจริง** เก็บ production render ของทุก screen family พร้อม theme, text scale, viewport, route, seed data และ source snapshot แยก route ที่เปิดจริง ถูก gate และ legacy ออกจากกัน ตรวจ evidence คู่แข่งว่า original หรือ reconstructed ก่อนใช้เทียบ
2. **เทียบทิศทางภาพ** ทำหน้า “วันนี้”, คลังคำ, ฝึก และผลจากข้อมูล synthetic ชุดเดียวอย่างน้อยสองทิศทาง เลือกแบบแนะนำจากภาษาไทย การจัดกลุ่ม ความหนาแน่น และความต่อเนื่องของงานตามคำสั่งผู้ใช้ บันทึกข้อแลกเปลี่ยนก่อนยืนยัน token และองค์ประกอบถาวร
3. **ทำระบบใน Figcraft จากแบบแนะนำ** จัด foundations, components, interaction states, screen families และเชื่อมหนึ่งรอบเรียนครบ ใช้ component เดียวกันในทุกหน้าที่มีหน้าที่เดียวกัน ห้ามเรียก SVG board ว่าเป็นไฟล์ Figcraft ที่ sync แล้วหากยังไม่ได้ตรวจในเครื่องมือนั้น
4. **ทดสอบต้นแบบกับงานจริง** ให้ผู้ทดลองเริ่มแบบ guest เพิ่มคำแรก ฝึก ดูผล ซ่อมคำผิด และกลับมาทบทวน บันทึกจุดลังเลและทางผิด แยกความเห็นของผู้ใช้ กรรมการ และ AI reviewer อย่างชัดเจน
5. **ส่งต่อ implementation เป็นชุดที่ตรวจได้** ทำ shell และ core loop ก่อน ตามด้วยคลัง progress AI สื่อ และตั้งค่า ส่วนรางวัลใช้ระบบที่ตกลงแล้ว ทุกชุดจบด้วย current render และ review disposition ไม่เปิดฟีเจอร์เพราะมีแบบสวยแล้ว
6. **ตรวจรับครบระบบ** เปรียบเทียบ implementation กับต้นแบบที่เลือกบนหลักฐานปัจจุบัน บันทึก gap ที่ค้าง ไม่อ้าง production readiness หากยังขาด physical-device, authority หรือ release acceptance

แต่ละช่วงต้องมี artifact ที่ผู้ใช้ตรวจได้พร้อม source หรือ design revision, ขอบเขตที่ตรวจ และคำตัดสินแก้ก่อนรับหรือรับได้ การผ่าน automated test ไม่ใช้แทนคำตัดสินงานภาพ

## เกณฑ์ก่อนเรียกว่างานออกแบบเสร็จ

- ทุกไฟล์ในบัญชีมี disposition ว่าใช้ร่วม ออกแบบใหม่ ถูก gate หรือ legacy พร้อมเหตุผล ไม่มีหน้าถูกหลงลืมเพราะไม่อยู่ในเมนูหลัก
- เมนูและคำสั่งผู้ใช้เป็นภาษาไทยธรรมชาติทั้งหมด ตรวจศัพท์ซ้ำกับ glossary เดียวกัน ห้ามชื่อทางเทคนิคและคำแปลตรงตัวที่ผู้เรียนต้องตีความ
- กลุ่มเนื้อหาใช้แนวจัดวางและระยะห่างที่แสดงความสัมพันธ์ ไม่มีบัตรแยกเดี่ยวหรือช่องว่างมากโดยไม่มีหน้าที่ ตรวจภาพทั้งข้อมูลน้อยกับข้อมูลมากก่อนรับ ไม่ใช้เปอร์เซ็นต์พื้นที่เป็นตัวแทนคุณภาพ
- ภาพตรวจใช้ production M3Theme และ shell จริง แยก light และ dark ชุดตัวอักษรไทย 100% และ 200% รวม portrait และ landscape ที่ 360×800, 393×876 และ 412×915dp รวมจอ adaptive ตาม contract ที่เลือก
- loading, empty, success, validation error, storage error, offline, denied permission, provider unavailable และ gated state มีข้อความกับทางไปต่อ โดยใช้เฉพาะสถานะที่เกี่ยวข้องกับหน้านั้น
- ไม่มีข้อความไทยทับกันหรือ CTA สูญหาย มีการเลื่อนที่ค้นพบได้ keyboard ไม่บัง input หรือ action และ focus กลับบริบทเดิมหลัง dialog หรือ navigation
- TalkBack อ่านชื่อ บทบาท สถานะ และ error ตามลำดับ action แบบลากมีทางเลือกการแตะหรือ keyboard ความต่างสีของข้อความธรรมดาอย่างน้อย 4.5:1 ข้อความใหญ่และองค์ประกอบที่เกี่ยวข้องอย่างน้อย 3:1 ตรวจจากสีที่ render จริง
- คง touch target อย่างน้อย 48dp เคารพ reduced motion และไม่ใช้สีเป็นสัญญาณเพียงอย่างเดียว
- ทดลองบนอุปกรณ์จริงและ TalkBack แยกจาก widget tests กับ emulator ระบุรุ่น ระบบปฏิบัติการ การตั้งค่า และขอบเขตที่ทดสอบ ไม่อ้างจากชื่อไฟล์ภาพหรือ checkpoint เดิม
- คง feature catalog 8/44, EvidenceContext และ EventEnvelopeV2, learning/progress/reward authorities เดิม การวิจัยเป็นทางเลือกและ default-off ผู้ไม่ร่วมวิจัยต้องไม่มี research rows, events, outbox หรือ upload
- ความยินยอม การตรวจ owner การส่งข้อมูล AI และ research authority ต้องปรากฏตาม boundary จริง การออกแบบไม่อนุมัติ enrollment, deployment, real-data upload หรือการลบข้อมูล
- บันทึกว่า AI แนะนำทิศทางใดและเพราะหลักฐานอะไร แยกจากการตรวจรับของผู้ใช้หรือกรรมการจริง ไม่เติมคำว่า approved หรือคะแนนรวมจากการอนุมานของ AI

ขอบเขตที่ยังไม่ตรวจในรอบนี้: current live app, TalkBack, focus, ทุก route และอุปกรณ์จริง บัญชีหน้าจอเป็น coverage ของแผนออกแบบ ไม่ใช่หลักฐานว่าทุกหน้าถูกตรวจภาพหรือพร้อมเปิดใช้
